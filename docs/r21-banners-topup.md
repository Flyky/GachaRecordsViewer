# R21：管理员历史卡池刷新与原神充值

2026-10-28

## 历史卡池刷新

管理员页面新增独立的「历史卡池数据」卡片，显示来源、版本、时间段数量、覆盖起止时间、获取时间及内置／数据库缓存状态。点击「刷新历史卡池」后：

1. 从 GitHub 获取 paimon-moe 卡池文件的最新提交，再按固定 SHA 下载 `src/data/banners.js`。
2. 使用 Acorn 只解析 AST 中的字面量数据，不执行下载的 JavaScript。按当前物品字典的英文名映射角色 ID，检查日期、名单、大小与覆盖范围。
3. 成功写入数据库后切换当前实例数据，欧非分析刷新后立即使用；不会修改原始抽卡记录。
4. 网络、解析、覆盖范围退缩或保存失败时保留旧版。若缺少新角色 ID，先刷新物品字典再刷新历史卡池。

重启读取缓存，无缓存时使用内置数据；读取缓存失败时使用内置数据并显示提示。启动不会联网更新，也不增加环境变量或配置文件。分析响应增加 `bannerVersion`，前端将其纳入既有的一致性校验，避免混用刷新前后的统计。

数据来源及 MIT 声明沿用 [R20](r20-luck-analysis.md)。Docker 分发补充 `BANNERS_LICENSE`；新增运行依赖 [Acorn 8.19.0](https://github.com/acornjs/acorn) 用于安全解析公开数据文件。

## 原神充值使用

「米游社功能」页新增「原神充值」，目前仅支持已添加米游社账号下的**国服官服**角色。与侧栏所选抽卡档案无关，不接受输入任意他人 UID。

R22 修复官方商品金额为字符串时的兼容问题，并新增管理员充值开关；卡片是否显示及新请求是否可用由开关控制，详见 [R22](r22-topup-compatibility.md)。

1. 选择米游社账号，点击「加载／刷新角色与商品」。服务端核实凭证归属，从官方重新取得官服角色、充值商品、人民币价格、可购买状态和支付宝／微信通道。
2. 选择商品和支付方式，点击「核对充值信息」。此时只生成本地确认信息，尚不创建官方订单。
3. 在确认框核对米游社账号、官服 UID、商品、数量 1、金额和支付方式。点击「确认创建订单并生成二维码」才开始创建官方订单。
4. 使用支付宝／微信扫码付款。原生二维码或官方收银页面二维码由官方当次返回的数据决定；页面显示二维码剩余展示时间。不会自动重新创建过期二维码。
5. 支付后点击「查询支付结果」。只有官方订单状态确认成功时，才显示支付成功；扫码、关闭确认框或点击查询都不会直接当作付款成功。

本轮不实现批量充值、优惠券、购物车、退款、取消官方订单、渠道服或其他游戏。可购买商品和实际支付资格以官方返回为准。遇到安全验证、风控、未开放的商品或接口适配变化，页面引导使用[原神官方充值中心](https://pay.mihoyo.com/ys/index.html)，不尝试绕过验证。

### 订单与重复提交

- 确认信息有效 5 分钟。下单前重新核对角色归属、凭证版本、商品名称、可购买状态、价格、价格档位及支付方式；变化时要求重新核对。
- 每次确认绑定一个请求 ID；创建官方订单前先在数据库登记。同一个 ID 重复提交只返回已有订单，不再次请求官方创建。
- 本地账号同时保留一个未处理的充值流程，网络结果不明也占用该流程，避免用户误触后再次创建。
- 创建订单或生成二维码只尝试一次。超时、断网或未知响应可能发生在官方已经创建订单之后，因此保存为「下单结果未确认」，不自动重试。
- 重新打开页面可恢复最近 20 条本应用创建的订单；重启后遗留的创建中记录转为待核实，不自动重新下单。已获得官方订单号的流程可以继续只读查询。
- 「结束本地跟踪」会清除本页二维码和加密支付上下文，保留订单摘要，允许用户重新核对商品。**不会取消官方订单，也不会退款**；确认框明确说明这一点，应先核实实际支付结果。
- 二维码展示到期后隐藏，仍可查询订单；不将二维码过期等同于官方订单取消或支付失败。

### 凭证与数据

复用已有 Cookie Token；仅在缺少 Cookie Token 且存在可用 SToken／mid 时换取。每次官方操作前后核对账号归属与凭证版本，解绑／替换授权后不继续提供旧二维码或使用旧凭证。

金额使用整数「分」，商品 ID、价格和价格档位来自服务端实时读取，客户端不能指定价格。业务订单签名、支付 JWT、Cookie 和完整上游响应不进入前端；前端仅接收本人订单摘要与临时付款二维码内容。支付 JWT／二维码上下文使用现有部署密钥加密保存，支付确认成功或结束本地跟踪后清除密文。配置密钥与数据库仍应一起备份，存在支付密文时也禁止无条件重新绑定另一把密钥。

服务端只访问固定的官方 API，不跟随返回 URL；原生二维码只接受已支持的支付宝／微信地址，官方收银页面只使用固定官方地址构造。响应禁止缓存，复用用户登录、Origin 和 CSRF 保护，请求与错误日志不记录凭证或上游原始消息。订单在本地用户之间隔离。

## 接口

路径相对应用根目录，部署在 `/gacha/` 时自动带该前缀。所有 POST 都需要对应登录会话、Origin、JSON 与 CSRF。

| 接口 | 权限／输入 | 结果 |
| --- | --- | --- |
| `GET /api/admin/banners` | 管理员 | 卡池版本、覆盖范围与缓存状态 |
| `POST /api/admin/banners/refresh` | 管理员；`{}` | 下载、保存并切换卡池数据 |
| `POST /api/community/topup/catalog` | 用户；`{ communityAccountId, uid? }` | 本人官服角色、选中 UID、商品和支付方式 |
| `POST /api/community/topup/quote` | 用户；`{ communityAccountId, uid, goodsId, method }` | 5 分钟本地确认信息 |
| `POST /api/community/topup/orders` | 用户；`{ quoteId, requestId }` | 幂等创建订单和付款二维码，或待核实状态 |
| `GET /api/community/topup/orders` | 用户 | 最近 20 条本人订单，符合条件时附有效二维码 |
| `POST /api/community/topup/orders/:orderId/check` | 用户；`{}` | 向官方查询当前订单，确认支付结果 |
| `POST /api/community/topup/orders/:orderId/archive` | 用户；`{}` | 结束本地跟踪，清除支付密文，不取消官方订单 |

支付方式枚举为 `alipay`／`wechatpay`。本地确认的 `amount` 与订单的 `amount` 均为人民币分；业务订单号和 UID 均保持字符串，避免整数精度丢失。

## 部署与升级

SQLite／PostgreSQL 分别新增 `0002` 迁移，添加 `shared_snapshots`（公共卡池缓存）和 `payment_orders`（用户订单及加密支付上下文）两张表，不改写已有账号、抽卡记录、凭证或配置。仍按原流程安装依赖、构建并启动；启动会执行已有迁移机制。Docker 需要重新构建镜像。

无需额外支付商户配置。这里调用官方充值服务，不使用自己的支付宝／微信商户收款。官方接口属于内部协议，后续可能需要跟随官方升级适配。

- 本地合成测试覆盖管理员／用户权限、CSRF、卡池解析和缓存、覆盖回退拒绝、刷新后分析版本、三方协议字段、官服角色过滤、两种二维码路径、价格变化、幂等、超时不重试、订单恢复、密文及密钥绑定。

- 未使用任何已保存真实米游社凭证，未创建真实待支付订单，未执行扫码或付款，未运行浏览器与 Docker 验证。合成测试不代表真实账号下单链路已经验收；真实二维码仍需用户在准备好后验证。
