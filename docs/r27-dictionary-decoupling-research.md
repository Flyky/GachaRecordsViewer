# R27 调研：物品字典与抓取、卡池、分析解耦

日期：2026-11-04。状态：调查与方案，尚未实施。

## 结论

可行。把「能否保存抽卡／卡池原始数据」与「能否解析标准物品 ID」分开：缺字典时照常保存，标记待解析；字典更新后补充解析结果，不要求重新从米游社抓取，也不改写已有历史事实。

能够解除记录抓取、保存、基础查询统计、历史卡池更新对字典完整性的硬依赖。跨语言物品对应、严格标准 ID 导出和部分 UP 判断仍需要可靠映射；无法凭现有原文确定时应明确未知，而不是猜测。

本轮只读源码和公开资料，未使用真实凭证或请求个人祈愿数据，没有修改业务代码／数据库，没有运行测试。

## 当前为什么会报错

| 环节 | 已核对的行为 |
| --- | --- |
| 上游解析 | `packages/providers/src/miyoushe/client.ts` 的 `parseWishPage` 已允许 `item_id` 为空，并保留名称、类型、星级、时间、记录 ID 等字段。缺标准 ID 不等于缺抽卡原文。 |
| 米游社刷新 | `apps/server/src/community/sync.ts` 遇到空 ID 时按简中名称＋类型＋星级查字典，匹配失败抛 `ITEM_ID_UNRESOLVED`。映射发生在整页入库之前，同页其他记录也不会写入。 |
| 祈愿链接导入 | `apps/server/src/wish-link.ts` 有相同的前置反查和拒绝逻辑，需要一并改造。 |
| 历史卡池 | `apps/server/src/banners.ts` 将 paimon.moe 的英文角色标识立即转换成字典 ID；任意一个未知就拒绝整次刷新。手动快照也检查所有 ID 必须已在字典中。 |
| 数据库／核心类型 | SQLite、PostgreSQL 的 `gacha_records.item_id` 都是 NOT NULL；ImportRecord、GachaRecord 及统计代码都假定 ID 是数字字符串。不能只删除报错语句。 |
| 去重合并 | 记录主键已经是档案＋抽卡记录 ID，有利于保持历史稳定。但现有合并会把 itemId 不一致视为冲突，需要区分「空 ID 得到补全」和「两个已知 ID 冲突」。 |

如果上游直接给出合法的非空 `item_id`，当前在线刷新本来就能接收字典尚未收录的 ID。主要阻断点是空 ID 必须提前反查成功，而不是所有新物品都被禁止保存。

UIGF 项目收集的接口资料显示，原神祈愿记录包含 `name`、`item_type`、`rank_type`、`time`、记录 `id`，并注明 `item_id` 可能为空。这是社区维护的协议资料，不能视为米哈游对未来响应的保证；与本项目现有解析器和合成测试契约相符。[祈愿接口资料](https://uigf.org/zh/mihoyo-api-collection/hoyolab/user/game_account_info.html#获取祈愿记录)

paimon.moe 的卡池源本身保存时间及 `featured` 中的英文角色标识，例如 `hu_tao`；把它们全部转成标准 ID 是本应用当前的适配要求。[上游源文件](https://raw.githubusercontent.com/MadeBaruna/paimon-moe/main/src/data/banners.js)

## 建议的数据规则

### 1. 原始记录始终可保存

- 以现有档案＋抽卡记录 ID 保持唯一性，分页与游标仍使用抽卡记录 ID。
- 保存上游原始名称、语言、类型、星级、时间、池类型及原始物品 ID；原始 ID 为空就如实为空。
- 将标准物品 ID 改为可缺失，并与本地分组标识分开。待解析记录不使用 `0`、负数、名称哈希等冒充游戏内部 ID。
- 增加或提供解析状态：来源已提供、字典匹配、待解析、存在歧义、信息冲突。记录 ID 缺失、UID 不一致、非法时间／池类型等协议错误继续处理，不能因解耦而跳过事实校验。
- 每页已知与待解析记录一起事务保存后才推进游标、检查点，避免后续增量刷新漏掉未保存的数据。

现有 `metadata_json` 已保留一部分原文，可复用。旧记录无法可靠还原当初的 ID 来自上游还是字典推断，迁移时应保留已有 ID、标为既有来源，不猜测或重建历史。

### 2. 字典作为补充解析层

读取时先使用原记录提供的数据，再用字典补全缺失关联；可以缓存解析结果，但缓存必须绑定字典版本。字典更新后重新解析待确认项，无需让用户重新抓取或导入。

- 唯一匹配时提供有效标准 ID；不唯一时继续保持待确认。
- 原始表不必因为字典更新而整表重写；已有可信标准 ID 不自动替换，原始名称、星级、类型、时间和记录 ID 保持。
- 另一份 UIGF／在线记录提供相同抽卡 ID 的可信物品 ID 时，可作为原记录的补充，不新增一条抽卡；两个非空 ID 不一致继续提示冲突。
- 多语言、改名、同名物品需按游戏、语言、类型、星级及来源约束消歧；不能只靠模糊名称匹配。用户上传数据得到的私有对应关系不应自动变成影响其他账号的全局字典。

更换字典后，待解析条目加入统计、多个临时分组归并、UP 判断从未知变为已知，可能让分析结果更完整。这是解析结果改善；不应承诺所有统计数字永远不变。原始抽卡数量和事实必须保持不变。

### 3. 历史卡池先保存原始名单

保存源时间、英文标识／名称以及源版本；如果输入已有标准 ID，也一并保存。刷新完成可以显示「已保存，部分角色待解析」，不要求所有角色事先在字典中。

派生的可用 UP 名单按「卡池源版本＋字典版本」生成并缓存，字典更新后重新解析，避免必须再次下载卡池才能识别新角色。保留旧版卡池缓存兼容，继续检查格式与覆盖范围。

英文标识与在线记录的中文名称之间没有可靠映射时，无法直接断言两者是同一角色。此时先保存两端原文，等待字典或其他可信别名映射。

## 各功能能保留到什么程度

| 功能 | 没有标准物品 ID 时建议的行为 |
| --- | --- |
| 米游社刷新／祈愿链接导入 | 正常抓取并保存，提示待解析数量，不中断整池或整页。 |
| 查询筛选、分页、颜色 | 使用原始名称、星级、类型、时间和卡池。缺少哪个字段，仅对应筛选／展示能力受限。 |
| 总抽数、年月统计、热力图 | 按真实记录、时间与池类型统计，不需要物品字典。五星计数依赖可靠星级，而不是标准物品 ID。 |
| 保底内抽数、五星平均间隔 | 星级与历史边界足够时继续计算；未知星级或已知缺口仍保留原有不确定性。 |
| 物品分组 | 待解析项按带游戏／语言／类型／星级的原文临时分组并标注；补全后按标准 ID 重新聚合，不合并或删除原始抽卡。 |
| 歪／不歪、UP 成本、连歪／连胜 | 对能够证明的结果计算；未知成员／无法对应的角色标为未知，避免污染结果和连续状态。 |
| 祈愿链接／米游社 API 模拟 | 可以按原接口语义输出空 item_id 与其余原始字段；页面提示第三方工具未必能导入这类条目。 |
| 完整 UIGF 导出与 UIGF API 模拟 | 需要明确处理未补全标准 ID，不能冒充已完成的标准导出。建议默认提示阻止完整导出，并提供独立无损原始备份；若增加「只导出已识别」选项，必须用户明确选择并显示遗漏数量。 |

欧非分析的关键边界：一个卡池窗口存在未解析 UP 成员时，「未命中已经识别的成员」不能直接判为歪；它可能命中尚未识别的成员。能够直接命中已知 UP 可判定命中，但负面结论和后续保底状态要保守处理。

UIGF v4.x 的原神记录要求 `item_id` 字段，语义为物品内部 ID。JSON Schema 对字符串的结构约束不等于允许拿任意临时值充当真实 ID。因此「先存原始记录」与「立即完成标准导出」需要分开处理。[UIGF 标准](https://uigf.org/zh/standards/uigf.html)

## 改动范围与实施建议

这是一次贯穿数据模型的调整：需要 SQLite／PostgreSQL 的兼容迁移，统一修改在线刷新、祈愿链接、UIGF 合并、查询分析、卡池缓存、API 模拟及导出。已有 dictionaryVersion、bannerVersion、dataVersion 可继续用于缓存／预览一致性控制。

建议按以下顺序实施并分别提交：

1. 数据模型、原始信息与可缺失 ID、两种在线入口及去重合并；确保资料先完整落库。
2. 查询／统计支持待解析记录，更新字典后的解析和缓存失效规则。
3. 卡池原始名单保存与保守 UP 判断、导出提示和无损备份，回归旧数据升级。

优先验证：一页含新角色仍完整保存；重复刷新不重复计数；更新字典后无需重抓取就能解析；补充 UIGF 只丰富原记录；歧义不乱配；未解析 UP 不误判为歪；无损备份完整；旧 SQLite／PostgreSQL 数据迁移前后数量及原始字段保持。

多数据源可作为额外补充，但它们也可能缺新物品，解耦不应以任何第三方源永远及时更新为前提。本轮核对的 UIGF CurrentBannerWatcher 仍会通过 UIGF 接口按名称反查 ID，不能仅凭更换它就假设消除了物品字典依赖。[其上游实现](https://github.com/UIGF-org/CurrentBannerWatcher/blob/main/main.py)
