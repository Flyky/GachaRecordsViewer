# R02 米游社授权最小验证工具

更新：2026-10-26

## 1. 用途与边界

这是开发阶段的命令行只读工具，不是正式登录或刷新页面。它验证国服原神的 App 扫码 → SToken → 凭证补充 → 绑定角色 → AuthKey → 少量祈愿分页链路。

- 不保存 SToken、LToken、Cookie Token、AuthKey 或完整上游响应。
- 不写数据库、不导出祈愿数据、不执行签到，不获取千星奇域记录。
- 默认一个卡池，最多两页、每页 5 条；只显示数量和脱敏结果。
- 用户必须在官方米游社 App 本人扫码确认；不接收米游社密码。
- 临时二维码在本机生成，不调用第三方二维码服务；仅存在被忽略的 `.probe/<随机会话>/qr.png`，正常结束、超时或取消后清理。
- 遇官方人机 / 实人验证要求时明确停止，不通过更换接口或重复请求绕开。

## 2. 运行

先选择 Node.js 24 LTS，安装锁定依赖：

```sh
pnpm install --frozen-lockfile
pnpm probe:miyoushe --help
```

验证官服，限定角色活动池两页：

```sh
pnpm probe:miyoushe --region cn_gf01 --pool 301 --pages 2
```

命令输出本机二维码图片的绝对路径。打开该 PNG，用官方米游社 App 扫码并确认；工具会显示等待 / 已扫描 / 已确认状态。默认等待最多 180 秒，也会遵循上游 URL 中更短的有效期。Ctrl+C 取消。

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--region` | 不筛选 | `cn_gf01` 官服，`cn_qd01` 渠道服；选择范围不是验证结果 |
| `--uid` | 不指定 | 目标游戏 UID 必须在当前扫码账号的绑定列表内 |
| `--pool` | `301` | 允许 `100/200/301/302/500`，不包括千星奇域 |
| `--pages` | `2` | 仅允许 1 或 2，每页 5 条 |
| `--wait-seconds` | `180` | 整数秒，允许 1–180 |

如果选择范围内有且只有一个档案，工具选用该档案；多个档案时必须再用 `--uid` 指定。即使输入了一个有效格式 UID，它不在本次扫码账号的角色列表中也会被拒绝。

同一次执行内使用相同设备上下文，结束后丢弃。当前使用参考项目 2.115.0 对应的公开协议参数与默认设备指纹初始化值；以后上游变动需要重新验证，不把本次通过视为长期保证。

## 3. 输出与失败处理

成功结果使用 `result=sample_verified`，包含脱敏 UID、服务器、卡池、已读页数 / 条数、三类凭证是否取得及 `persisted=false`。不会打印 Token、完整 UID、手机号、二维码 URL、原始响应或祈愿明细。

`reachedEnd=false` 表示在两页上限时仍有记录，不是全历史已抓完。空池结果只能证明选定范围请求成功，不能证明保存历史完整。

| 错误类型 | 含义 / 处理 |
| --- | --- |
| `expired` | 二维码本地 / 上游有效期已到，重新运行 |
| `cancelled` | 用户取消或中止进程 |
| `verification_required` | 官方验证要求，终止本轮并通过官方流程处理 |
| `auth_invalid` | 上游拒绝凭证；重新授权 |
| `role_required` | 选择范围没有唯一目标，明确 `--region` / `--uid` |
| `role_mismatch` | UID 不在绑定列表、身份不一致或祈愿返回的角色 / 池不符；停止，不替换成其他 UID |
| `network` / `timeout` | 请求失败或超时；检查网络后手动重试，工具不无限重试 |
| `protocol` | 参数或上游返回结构不符合预期；核对现行协议，不记录原始敏感响应 |
| `upstream` | 其他业务 / HTTP 错误，只输出阶段与数字错误码 |

普通 LToken 补充失败可以标记该能力不可用，继续检查其余必需链路；遇官方验证或取消则立即停止，不尝试替代流程。

正常退出会清理二维码。进程被操作系统强制结束时清理逻辑可能无法执行；其二维码仍会过期，但 `.probe/` 内的文件也不应公开提交或分享。

## 4. 本轮真实验证记录

环境：2026-10-26，本机 Windows，已有 Node.js 24.22.1，当前机器网络，官方米游社 App 扫码；协议参考 TeyvatGuide 固定提交 `72c3f371673e40cf0c2153535ddddafd24462fbc`。

| 项目 | 结果 |
| --- | --- |
| 第一次扫码 | 成功确认，取得 SToken、LToken、Cookie Token 和角色列表 |
| UID 检查 | 原 UIGF 样例的 UID 不在本次授权列表，正确拒绝；未为其他 UID 请求祈愿 AuthKey |
| 选择目标 | 用户明确选择官服档案 `10***44`，第二次重新扫码 |
| 官服授权链路 | 成功创建 / 轮询 App 二维码，取得 SToken、LToken 和 Cookie Token，Cookie 账号 ID 校验一致 |
| 绑定角色 | 返回官服与渠道服档案；本次只选官服 `cn_gf01` |
| 原神 AuthKey | 为选定官服档案成功生成 `webview_gacha` AuthKey |
| 祈愿读取 | 角色活动池 `301` 两页，每页 5 条，共 10 条；逐条校验 UID、池、无损 ID 和游标顺序 |
| 完整性 | `reachedEnd=false`；未抓取全部历史 |
| 数据保存 | `persisted=false`，未保存凭证或抽卡明细；两次二维码 PNG 均已清理 |

**本轮通过范围：当前环境、用户指定的官服档案、角色池 10 条只读样本。**

以下未在本轮完成真实验证：渠道服祈愿、其他原神卡池、国际服、星铁、全量 / 增量同步入库、重启保存授权、最终服务器部署网络。这些不会因角色列表出现过相应账号而自动标为支持。

用户已补充该官服档案的 UIGF v4.1 文件。本轮只读校验通过，包含 11,326 条记录（角色池 7,356、武器池 2,793、常驻 1,157、新手 20）。它将作为后续导入与查询的本地参考；未提交原始文件，也未进行旧格式迁移。该历史文件与在线抽样是两个独立验证，不宣称已逐条对账。

## 5. 自动化验证与来源

provider 使用注入式 HTTP transport 测试请求、状态与失败；测试数据完全合成。固定 DS 测试向量由独立 .NET MD5 计算核对。测试覆盖：

- 空对象扫码请求、设备上下文保持、重定向禁止与二维码域名限制。
- 等待、已扫描、确认、超时、取消、缺字段、错误 Token 类型与官方验证。
- 网络 / HTTP / 业务错误不反射上游消息、URL、凭证或原始异常。
- 账号不一致、未绑定 UID、多档案选择、明确服务器选择。
- 大整数 ID、`301/400` 归组、游标推进、不同 UID / 卡池、不正确顺序、过大页面。
- 最多两页、不做全量抓取，状态与结果仅输出白名单字段。

运行：`pnpm test`。本轮包含 R01 原有 8 项与 provider 49 项，共 57 项通过。
