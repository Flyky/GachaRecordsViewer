# R13 内置 App 扫码授权后端

日期：2026-10-27。代码与两库模拟传输验证已完成；正式 API 的真实扫码、重授权及保存后上游复用已通过本机验证。该结果限定于下文环境和授权操作，不代表抽卡刷新已验收。

本轮将 R02 的 App 扫码协议接入本地认证与 R12 加密存储，不提供前端账号页面，也不拉取抽卡历史。页面留给 R15，刷新任务留给 R14。外部网页登录所得 Cookie／LToken 可继续通过 [手动凭证接口](community-api.md) 导入，其能力与 App 扫码得到的 SToken 分别判断。

## 调用流程

所有接口要求普通用户登录；写请求要求 JSON、配置 Origin 和会话绑定 `X-CSRF-Token`，参见 [认证 API](auth-api.md)。会话归属于创建时的 owner 和本地登录 session；同一个用户的另一次登录也不能取得、轮询或取消原票据。没有管理员代查入口。

| 方法与路径 | 请求体 | 返回 |
| --- | --- | --- |
| `POST /api/community/qr` | `{}`，或 `{ "communityAccountId": "本应用已有米游社账号 ID" }` | 201，`{ session, qrUrl }` |
| `GET /api/community/qr/:id` | 无 | `{ session }`，只读当前本地状态，不调用上游轮询 |
| `POST /api/community/qr/:id/poll` | `{}` | `{ session }`，有界查询上游；确认后验证并保存授权 |
| `POST /api/community/qr/:id/cancel` | `{}` | `{ session }`，取消未进入落库阶段的授权 |

`session` 包含 id、status、expiresAt、pollAfterMs；成功时增加 communityAccountId，失败时增加固定 code。除创建响应外，不返回二维码 URL、上游 ticket、Token、mid、账号个人资料或密文。所有响应 `no-store`，日志不记录响应体、二维码 URL 或凭证。

前端先创建会话，将 `qrUrl` 在本地编码为二维码，使用官方米游社 App 扫描并确认。不要把二维码载荷交给第三方在线生成服务。之后按 `pollAfterMs` 查询，建议至少间隔 2 秒；`GET` 本地状态不推进上游状态。二维码 URL 只在创建时返回；刷新页面后可凭原会话 ID 取消再创建，不能据状态接口恢复载荷。

新授权使用 `{}`，重复米游社身份不会自动覆盖已有账号；重新授权必须显式提交当前用户的 communityAccountId。服务在创建二维码前记录目标身份和凭证版本，确认后检查身份一致、目标未解绑且凭证未被其他操作替换。保存成功沿用原社区账号和档案 ID；不同身份、陈旧版本或绑定冲突都不覆盖原凭证。

## 状态和并发

| status | 含义与后续操作 |
| --- | --- |
| creating | 内部正在创建上游票据，创建接口完成后才返回 waiting |
| waiting | 等待扫描，继续有界轮询 |
| scanned | 已扫描、等待 App 确认，继续轮询；迟到 Init 不会使状态回退 |
| confirming | 已取得确认结果，正在校验和保存；不会再次请求同一票据 |
| confirmed | 已加密保存，返回本地社区账号 ID；重复 poll 返回相同结果，不再次换取或保存 Token |
| cancelled | 用户或上游取消，终态 |
| expired | 本地／上游到期或达到轮询上限，终态 |
| verification_required | 上游要求额外验证，停止；通过官方流程处理后重新创建或手动导入 |
| failed | 网络、协议、凭证、目标冲突或保存失败，终态，code 给出固定原因 |

一位本地用户同时最多一个活动扫码会话。创建期间也先占位，避免同时创建多张票据；冲突返回 `409 QR_ALREADY_ACTIVE`。创建独立限速为每用户 10 次／15 分钟、每 IP 20 次／15 分钟，超限 429 与 Retry-After。

二维码最多有效 180 秒，并服从上游更短有效期；创建和凭证验证的时间也计入期限。每会话最多 90 次上游查询、两次查询开始至少间隔 2 秒，单次上游请求沿用 provider 的 10 秒超时。提前或并发 poll 只返回本地状态和下一次间隔，不触发重复查询。服务端不在后台自动轮询，不因网络／验证挑战反复重试。

取消会清除内存票据并中止请求；即使迟到响应忽略中止，也必须在落库前通过有效期与状态检查。取消和 expired 终态不会重新变为 confirmed。进入数据库原子保存阶段后，取消返回 `409 QR_COMMITTING`，客户端应继续读取状态；已完成授权返回 `409 QR_ALREADY_CONFIRMED`，删除已保存授权应使用账号解绑接口。取消本地会话不等同于撤销上游已经签发的凭证。

持久化事务内再次核对原本地 session 是否有效、属于该用户且未因改密失效；PostgreSQL 锁定对应用户与会话行，SQLite 通过写事务串行执行。事务开始和完成前检查二维码期限；逾期整体回滚。二维码确认阶段与手动替换／解绑共享 R12 的 owner 操作锁，目标凭证版本检查阻止其他进程的迟到覆盖。

活动和终态均仅存在单个服务进程内；每 5 秒清理过期票据，终态保留 5 分钟供客户端读取，之后返回 `404 QR_NOT_FOUND`。内存最多保留 128 个会话。服务重启、关闭会清除临时会话并中止请求；已保存的加密凭证和设备上下文保留，可供后续校验／刷新使用。当前部署为单进程；多实例负载均衡下不能跨实例接力扫码。

## 保存和失败

同一次扫码的创建、查询和凭证校验使用相同设备上下文。只有 R12 的身份与角色校验成功才整组加密保存 SToken、已验证的派生 Token 和设备信息；默认响应只显示能力和遮挡值。LToken 的可选补充失败不冒充有效，验证挑战则停止整个流程。加密、备份、本人 reveal、解绑保留历史规则见 [R12 文档](community-api.md)。

保存的 wish 仍为 `unverified / authkey_not_checked`；本轮不会生成祈愿 AuthKey、读取记录或创建同步任务。首次绑定可能列出官服与渠道服档案，但不能据此宣称两种服务器的祈愿刷新均已实测。

固定错误包括 QR_NOT_FOUND、QR_ALREADY_ACTIVE、QR_CAPACITY、QR_UNAVAILABLE、QR_COMMITTING、QR_ALREADY_CONFIRMED、QR_EXPIRED、QR_POLL_LIMIT、QR_SESSION_INVALID，以及 R12 的身份／凭证版本／绑定错误。创建失败使用 R12 HTTP 错误映射；poll 中的失败体现在 200 响应的终态 status 和 code，不以 HTTP 200 代表授权成功。未知异常仅返回 QR_FAILED，不反射原始上游信息。失败后可以重新创建或使用手动导入。

## 验证与本人扫码安排

本轮 28 项定向集成测试通过：SQLite／真实 PostgreSQL 各 9 组扫码契约与各 5 组 R12 回归。覆盖等待／扫描／确认、一次消费、设备一致、重启复用、owner 与本地 session 归属、CSRF、取消／过期／退出后的迟到凭证、并发轮询、重新授权、身份不符、版本变化、失败终态、有限轮询、内存票据清理和日志脱敏。受影响类型、零警告 lint、后端与依赖构建通过；未重跑浏览器、前端构建或无关全量。

真实扫码安排在独立工作全部完成之后，先询问用户、收到肯定回复后才创建二维码与开始轮询。用户已允许本地加密保存 Token 供后续测试复用，正常情况下不反复请求重新扫码，凭证失效时再授权。
