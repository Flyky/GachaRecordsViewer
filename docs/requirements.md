# Gacha Viewer 需求规格与验收标准

日期：2026-10-26

版本：讨论稿 0.1

依据：用户本轮 12 条需求、旧版源码分析及本轮公开资料调研。

## 1. 产品目标与范围

为个人及少量朋友提供需要登录的原神抽卡记录保存、查询与分析 Web App。预计本地登录账号不超过 8 个，此数量是部署规模参考，不设置为业务上限。

本轮只产出需求、调研及技术方案文档。首期实现范围与尚未确定的建议分别标注。

### 1.1 三种账号必须区分

| 名称 | 含义 | 关系建议 |
| --- | --- | --- |
| 本地应用账号 | 管理员创建的用户名、密码；用于登录本 Web App | 每个账号拥有自己的记录及授权 |
| 米游社账号 | 米哈游通行证 / 社区身份及对应 Token | 一个本地账号可以管理多个；不与本地密码混用 |
| 游戏账号 / 档案 | 游戏、游戏 UID、服务器标识 | 一个米游社账号可对应多个游戏档案；也允许只有 UIGF 的离线档案 |

普通用户只能操作自己的数据。仅通过 UIGF 导入即可使用查询、统计和导出，不要求先绑定米游社。

## 2. 普通用户登录与密码

### 2.1 必须实现

- 登录页输入本地账号和密码。
- 不提供自助注册页面或公开注册 API。账号由管理员创建。
- 新账号的初始密码固定为 `12345678`。
- 使用初始密码登录后提示修改密码，可关闭或暂时忽略，继续正常使用。
- 提供修改自己密码的入口，校验当前密码。
- 提供退出登录。
- 数据导入、查询、统计、导出、米游社绑定和 Token 展示均要求用户登录。

### 2.2 建议的具体规则

- 每次仍使用初始密码登录时重新提醒；当前会话关闭提醒后不在每个页面反复弹出。
- 使用 `is_initial_password` 状态结合密码修改逻辑判断，不通过保存明文密码实现提醒。
- 管理员重置后恢复初始密码状态；修改为非初始密码后清除该状态。若主动设置回初始密码，继续提醒。
- 密码修改 / 重置使原有登录会话失效；密码修改成功后可重新建立当前设备会话。
- 账户名建议 3–32 位字母、数字、下划线、点或短横线，按规范化后的名称唯一；最终格式可在实现前调整。
- 普通密码建议至少 8 位；是否允许用户重新设置为初始密码不改变“不强制修改”的要求。

## 3. 管理员

### 3.1 入口

- 管理页通过直接输入 URL 访问，建议 `/admin`。
- 普通页面、登录页、菜单和页脚不提供管理页按钮或链接。
- 访问 URL 后仍需管理员认证；普通用户会话不能调用管理员 API。
- 管理页仅提供：创建普通账号、重置普通账号密码。用于选择重置对象的简单账号列表属于上述功能的必要辅助。
- 首期不增加用户删除、封禁、修改用户数据、查看用户 Token 等管理功能。

### 3.2 部署时的管理员密码

- 首次初始化、且配置中没有密码时生成随机管理员密码，写入持久化配置文件。
- 后续重启或重新部署沿用已保存密码，不反复生成。
- 可通过编辑配置文件修改密码；建议重启服务后生效，原管理员会话失效。
- 管理员身份建议固定为 `admin`，与普通用户数据库分离，并禁止创建同名普通账号。这是实现建议。
- 重置普通账号后不改变其记录、授权归属或历史导入数据。
- 建议重置密码为 `12345678`，需在重置确认界面明确显示结果；原需求未单独指定重置目标值。

## 4. 数据导入、保存与导出

### 4.1 UIGF 支持边界

- 正式导入格式使用 UIGF v4.0 及之后已实现的版本。
- 当前明确支持版本建议为 v4.0、v4.1、v4.2。未知未来 v4.x 先提示不支持，更新适配后开放；不能仅比较版本数就承诺无限向前兼容。
- 首期读取 `hk4e` 原神数据。
- 文件可包含多个游戏、多个 UID。导入前列出可导入的原神档案，允许选择，写入当前本地账号。
- `hkrpg`、`nap`、`hk4e_ugc` 首期跳过，并显示跳过的游戏 / 档案 / 记录数量；不把千星奇域混入原神祈愿。
- 当文件中没有可导入的原神记录时，明确提示，不显示虚假的“导入成功”。
- 不再提供旧 `biuuu/genshin-wish-export` 内部 `result/typeMap` JSON 的常驻导入入口，也不新增 UIGF v3 / SRGF v1 支持。
- 移除的是旧内部 JSON 格式支持；同一工具导出的合法 UIGF v4.x 文件仍可导入。

### 4.2 导入行为建议

1. 上传 JSON，限制大小并校验可解析性。
2. 按声明版本选用固定的 UIGF Schema，验证支持的游戏块和公共元数据。
3. 显示 UID、语言、时区、时间范围，以及新增 / 已有 / 冲突 / 跳过条数。
4. 用户选定档案后执行合并；每个选定档案以事务方式写入并报告结果，不隐式清空已有记录。
5. 导入失败时明确报告失败档案；重复导入不重复增加记录。

使用真实记录 ID 去重，唯一范围包含数据所有者、游戏档案及记录 ID。若同 ID 的关键字段冲突，报告冲突，不静默覆盖；名称和可补充元数据可按明确规则补全。

所有记录 ID 均以字符串保存及传输，排序使用无精度损失的十进制数值比较。保留原始卡池类型与 UIGF 保底分组类型，不能只留一个字段。

Schema 允许原神记录省略名称、物品类型和星级。此类文件仍可合法：通过本地物品字典补全，无法补全时保留必需原始字段并标记元数据未知，不能随意猜测星级或将其归为三星。相关筛选与保底结果提示不完整。

### 4.3 导出

- 登录用户可导出自己的原神档案，支持单 UID；多 UID 打包为一个 UIGF 文件是建议默认能力。
- 默认导出完整档案，包含数据库中长期保存的历史，而非只导出当前列表页。
- 原神建议默认导出 v4.0，因当前所需字段已可表示；若后续开放星铁联动池，使用 v4.1 或更高的对应 Schema。
- 输出标准要求的元信息、游戏 UID、时区、原始记录 ID、物品 ID、原始卡池类型及 UIGF 卡池类型。
- 可补充名称、星级等可选字段；导出前校验格式。
- UIGF 文件不包含米游社 Token、Cookie 或本地登录信息。
- 标准导出 / 再导入后，记录集合、ID、时间、卡池与 UID 不变。
- 应用说明中提供 UIGF 项目链接；格式支持不等同于已取得 UIGF 项目认证。

### 4.4 本地参考数据与旧格式边界

用户已明确：**旧 JSON 的历史迁移不做**。不开发旧格式解析入口、一次性转换器或旧表数据迁移工具；既有文件保留本地，不执行转换或删除。

改用用户提供的 `UIGF_v4.1_<uid>_<timestamp>.json` 作为实现参考。该文件已通过 UIGF v4.1 Schema 校验，包含一个原神档案、1,413 条记录，时区 `+8`、语言 `zh-cn`；必填的物品 ID、原始类型、保底分组、时间和字符串记录 ID 均齐全。

该真实文件仅在本地用于验证；提交到仓库的测试样例应另行合成或匿名化。标准导入导出保留历史的功能仍需实现，这与不做旧格式转换是不同的范围。

R02 用户另行补充了本次扫码官服档案的 UIGF v4.1 文件，含 11,326 条记录，也已通过标准校验。两份真实参考均保留本地，后续应覆盖小档案、多年大档案和不同本地用户 / UID 的隔离场景。

### 4.5 下一版：祈愿链接导入

用户已确认这是必要功能，安排下一版实现，不属于首版可选开关。

- 输入为本地游戏打开祈愿记录页后，从日志 / 缓存等位置提取出的包含临时 AuthKey 的祈愿 URL。
- 用户在本应用粘贴链接，服务端仅提取允许参数并调用固定上游接口，检查返回 UID 与选定档案一致后分页获取、去重合并。
- 无需为此绑定或长期保存 SToken / LToken。链接失效时提示重新取得，不承诺固定有效小时数。
- 纯网页不会自动读取玩家本地游戏缓存。提供链接提取说明，自动本地提取工具不作为本项的隐含要求。
- 不让服务端任意请求用户输入的 URL；沿用真实 ID 去重、档案归属检查及保留历史规则。

## 5. 米游社授权与在线刷新

### 5.1 确定需求

- 用户在本地账号下管理自己的米游社身份，选择游戏 UID 后刷新记录。
- 优先在本 Web App 内完成授权，提供扫码流程。
- 同时保留手动 Token / Cookie 导入，在页内展示获取手册。
- 在本人的授权详情中显示 SToken、LToken 等实际已取得的凭证；默认遮挡，主动查看 / 复制。
- 不能取得的凭证显示“未取得”及能力限制，不生成伪值。
- 展示授权是否有效、绑定角色、最后刷新时间、刷新结果和失败原因。

### 5.2 基于调研的实现建议

- 国服原神优先走米游社 **App 扫码接口**，服务端发起和轮询；扫码确认仍由本人在官方 App 完成。
- 扫码成功后取得 SToken 与账号标识，按需补充 LToken / Cookie Token、列出绑定角色，再生成 `webview_gacha` AuthKey 获取祈愿记录。
- 普通网页登录 Cookie 或网页扫码不保证包含 SToken；允许导入，但必须分别验证“身份 / 战绩可用”和“祈愿刷新可用”。
- 若遇官方验证、设备校验或风险提示，显示待用户处理状态；不以重复高速请求替代处理。
- 刷新为用户手动触发，首期不自动定时抓取，也不自动签到。
- 每个游戏档案同时只运行一个刷新任务；显示分卡池进度，失败可重试。
- 刷新数据以 ID 合并，不能因上游已看不到旧记录而删除本地历史。
- 上游仅返回有限时间窗口内记录，不能承诺凭 Token 恢复账号开服以来全部历史。
- 解除绑定删除本地保存的对应凭证，默认保留已导入抽卡档案；本地解绑不等于撤销上游所有登录状态。

### 5.3 尚未验证的边界

R02 已使用本人扫码取得 SToken / LToken / Cookie Token，验证角色归属、官服原神 AuthKey 及角色池两页 10 条只读记录。详见[实测记录](miyoushe-probe.md)。渠道服、其他池、全量 / 增量入库、授权持久化与最终部署出口仍需实测；任何一步失败都保留 UIGF 离线功能与获取手册。

HoYoLAB 国际服及星铁的授权能力另行适配，不能直接套用国服原神的成功结论。

## 6. 查询记录：保留全部既有能力

| 项目 | 必须行为 |
| --- | --- |
| 时间范围 | 起止日期时间筛选；保留旧版最近一周 / 一月 / 三月快捷项 |
| 卡池 | 多选，包含新手、常驻、角色活动、武器活动、集录；不选表示全部 |
| 物品类型 | 角色 / 武器，保留旧版多选能力；不选表示全部 |
| 稀有度 | 三星、四星、五星，保留多选；不选表示全部 |
| 名称 | 子串模糊匹配，按字面处理 `%`、`_` 等 SQL 通配符 |
| 顺序 | 时间正序 / 倒序；同一秒内用记录 ID 保证稳定顺序 |
| 基本列 | 时间、物品名称、星级、卡池类型 |
| 可选列 | 卡池类别内总次数、保底内次数，独立开关 |
| 字色 | 物品名称按星级区分；建议五星金、四星紫、三星蓝，保留文字星级便于辨认 |
| 分页 | 页码跳转、总条数、20/50/100/200 条每页；查询改变时回到第一页 |

建议使用后端分页，以保持功能一致并减少传输。查询与统计始终限定当前用户和当前游戏档案，不跨朋友的账号合并。

### 6.1 次数的定义

- “总次数”是当前档案、对应 UIGF 卡池组内保存记录的累计序号，不是筛选结果里的行号；界面补充“已保存记录内累计”的说明。
- “保底内次数”保留旧定义：五星间隔计数，五星后下一抽从 1 开始；不是剩余保底抽数，也不代表大小保底判断。
- 角色活动原始类型 `301` 与 `400` 的序号和五星间隔共用 `301` 组；其他组相互独立。
- 必须先按完整历史计算，再筛选、排序、分页；筛选四星或倒序时不能重新计数。
- 最早记录不代表建号第一抽。第一次可见五星之前的间隔，以及已知缺口后的区间，标记为“已知记录内 / 可能不完整”；不能伪装成完整出金抽数。
- 补入更早历史后，重算受影响档案的累计值与统计；不能只在导入时追加一个永久序号。
- 星级未知导致无法判断是否五星重置时，不输出确定的连续保底值，待元数据补全后计算。

## 7. 统计分析：原功能全部保留

### 7.1 物品分组统计

- 角色 / 武器切换。
- 角色按五星、四星分栏；武器按五星、四星、三星分栏。
- 每栏显示名称、获得数量，支持数量排序。
- 以物品 ID 聚合，名称作为展示值，避免不同语言的同一物品重复计数。
- 元数据未知的记录单独提示，不算入错误星级分栏。

### 7.2 年月分组折线图

- 保留总抽数、五星数、常驻池、角色活动池、武器活动池五条系列，图例可切换，时间轴可缩放。
- 总抽数包含首期支持的所有原神祈愿类型；新手 / 集录的单独系列可作为后续小幅增强，不替代现有系列。
- 年月顺序明确排序，记录覆盖范围内缺少抽卡的月份补 0。
- 月份按所选游戏档案的游戏时区归属；五星未知时提示统计不完整。

### 7.3 Daily 热力图

- 年份默认用户当天所在时区的当前年份；默认 Asia/Shanghai，可在后续个人设置扩展。
- 卡池默认不选，表示全部类型一起统计；选择卡池后只统计该类型。
- 年份列表覆盖已有记录年份及当前年。
- 完整绘制当年日历，包括闰日；没有抽卡的日期仍可 hover，显示 0 抽。
- hover 单日显示日期与当日抽数。示例：`2026-10-26 · 10 抽`。
- 没有记录时显示空状态和全 0 日历，不出现无效颜色比例。
- 每日按游戏档案时区统计，不能随服务端操作系统时区改变。

保留旧版查询与统计的独立筛选关系：查询页条件不会悄悄影响统计页；统计页仍作用于当前选定的游戏档案。

## 8. 数据库与运行规模

- 同时提供 SQLite 和 PostgreSQL 实现，在部署时配置。
- 默认 SQLite，数据库文件放在持久化数据目录。
- PostgreSQL 通过连接参数或连接字符串配置。
- 两种模式下账号、导入、去重、查询、分页和统计结果一致。
- SQLite 模式按单个服务实例设计，使用事务与写入串行化；8 个左右用户不需要引入分布式服务。
- 启动时执行对应数据库的结构迁移；已有数据的跨数据库搬迁不通过简单更改配置自动发生。

## 9. 新增分析提案：未视为已批准范围

| 优先级 | 提案 | 所需数据与限制 |
| --- | --- | --- |
| 建议优先 | 每池总抽数、五星数、当前距上次五星抽数 | 只依赖记录；历史不足时标明不确定 |
| 建议优先 | 五星获取时间线与每次间隔 | 完整五星区间可精确计算，首个区间可能不完整 |
| 可选 | 已完成五星区间的平均 / 中位 / 最短 / 最长抽数 | 排除不完整首段、缺口段和未完成末段，说明样本数 |
| 可选 | 每月各池抽卡占比、记录覆盖与导入来源概览 | 不需要推断 UP 规则 |
| 后续 | 卡池期次与 UP / 歪率分析 | 需要历史 UP 名单、时区、规则版本及复杂机制，不能仅凭常驻角色名单判定 |
| 后续 | 抽卡花费折算 | 只能标作抽数的资源等价，不当作真实消费金额 |

不建议首期展示“下一抽出金预测”或无解释的全服欧非排名。

## 11. 核心验收标准

1. 普通用户不能调用注册或管理员接口；管理员只能在独立管理入口创建账号、重置密码。
2. 新账号以 `12345678` 登录后收到非强制提醒；关闭后可查询和导入；重置后恢复提醒且旧会话失效。
3. A 用户不能通过修改请求中的 UID、档案 ID 或任务 ID 访问 B 用户记录、统计、导出或 Token。
4. 同一 UIGF 文件导入两次，第二次新增 0 条；后补更早历史不破坏记录 ID、排序和次数。
5. v4.0/v4.1/v4.2 原神样例能校验和导入；未知版本、错误字段、缺少必填字段有明确错误；缺少可选元数据不会被误判为必填失败。
6. 含千星奇域 / 星铁 / 绝区零的混合文件只导入选定原神档案，跳过项可见；没有原神块时明确提示。
7. 导出能通过对应 UIGF Schema 校验，再导入到空档案后记录集合一致，且文件不含 Token。
8. 组合筛选、同秒排序、分页、星级颜色和两项可选列正常；切换筛选不能改变某条记录的历史次数。
9. 五栏物品统计、月度五条系列、年度热力图与相同记录集合对得上；无记录、跨年、闰年和空卡池有效。
10. SQLite 与 PostgreSQL 跑同一组账号隔离、导入、查询和统计验收数据，结果一致。
11. 米游社凭证默认遮挡，查看只允许本人；失败 / 日志 / 任务列表中不出现完整 Token。
12. 用真实国服原神账号完成扫码 → SToken → 绑定角色 → AuthKey → 分页拉取 → 再次刷新新增为 0 的链路，才可标为已实测支持。
